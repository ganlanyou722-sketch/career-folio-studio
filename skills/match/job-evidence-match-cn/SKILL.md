# 岗位匹配分析台

输入为已核对的一个或多个 JD、当前意向、同一时间点的个人经历事实。职业入口沿用计算机、互联网、金融。具体岗位和业务对象决定检索与解释。没有 JD 时只给方向探索，用方向标签描述“哪些经历值得看”，等用户加入 JD 再给逐条结论。

1. 图片先核对 OCR，保留 JD 原句及定位。把复合句拆为可验证的职责或条件，合并重复表达；标“明确必需／普通职责／加分”，另记资格、工具、时长、学历等硬条件。只按 JD 真实措辞判断必需。意向单列，允许为空。
2. 对每条要求建立检索意图：工作对象、核心动作、交付物、预期结果、最低责任范围及限定。先按原词、别名、方法和交付物检索事实，再补检索语义相近的陈述；按项目 ID 取回上下文。复用内容台词库的词形和同义映射（如有），词库外的要求保留原句独立处理。职业方向不能成为排除跨行业实践的硬过滤条件。
3. 从候选事实回看原文和主体。直接支持是事实满足要求的关键动作及范围；部分支持要指出具体差的环节；资料缺失、冲突或归属未明标“待补信息”；只有与条件相反的确证才标“已知不满足”。仅有团队奖项无从证明本人带队，懂某个行业也无从证明持有从业资格。
4. 每条要求输出原句、类型、状态、带版本的事实引用、理由、仍缺什么和一个可选补问。可并列引用多个互补事实；一条事实若支持多个要求可重复引用，但同一要求只计一次。候选集全无匹配时，扩大召回或就缺口询问，不能用材料数量或关键词出现次数代替结论。
5. 比较多个 JD 时固定经历和意向快照。沿用 PRD 的默认排序：优先意向在前、可接受与未填居中、暂不考虑在后。组内明确必需项有已知缺口者后列；各层按（直接数＋0.5×部分数）／去重必需数降序，并列保留加入顺序。无明确必需项的 JD 在该意向组单列“条件待澄清”，继续比较职责。展示支持项、未知项及硬缺口数量，逐项可展开；该值只描述证据覆盖。资料很少时先提示补充有区分度的经历。
6. 为选中岗位生成交接。简历台获得“重点展开／压缩／略去”、对应事实、JD 原句及最多一个优先补问；已有简历只建议有依据的局部变化。面试台获得同一 JD 修订、实际投递稿修订（尚无则标草稿）、推荐案例、可讲的取舍、可能的追问、证据与缺口。公司的外部动态由面试台另取来源和日期。面试补充仅在本人确认同步后生成新事实修订，旧投递版仍固定。
7. 新版 JD、意向或相关事实出现时标注“资料有更新”，重算受影响的要求和排序。涉及新增事实时，要在所有活跃 JD 里检索其可能支持的要求，避免遗漏此前没有证据的岗位；既有投递与面试包使用创建时的快照。

样例见 [比较与交接](examples/match.json)。

如果用户已有简历，按[识别 JD 并生成岗位副本](references/jd-to-resume.md)直接接入简历优化台。
