# 好好投产品调优

## 产品基线

- 「好好投」服务两类场景。找第一份实习的人要从课程项目、竞赛和校园实践中筛出能写进简历的真实经历。同时看中几个岗位的人要用原稿和 JD 找出各岗位该突出的证据，再调顺序和措辞。
- 首页主句是「第一份简历写得出，换个岗位改得准。」品牌标志是羽毛笔在简化的牛皮纸上书写。四个入口卡是个人经历台、岗位匹配台、简历优化台和面试打磨台。
- 正式站是一套工作台，代码在 `main`。在现有模块里迭代，版本历史从 Git 查阅。旧产品页面和旧地址已移除。个人简历的底稿、岗位副本和定稿属于用户数据，已有记录应能继续打开。
- 业务技能位于仓库根目录的 `skills/`，由各工作台按需使用。调整界面手感时沿用业务技能。调整个性化建议时，定位到现有模块对应的技能包和调用链，用虚构简历和 JD 核对改写依据。

## 交互验收

- 视觉简约，组件有圆角。拖拽、悬停和动效要交代用户正在操作哪一项、它能放到哪、操作有没有完成。悬停用于预览和高亮。导入、开始分析、删除、定稿等明确动作通过点击或键盘确认。触屏和键盘用户也能完成相同操作。
- 个人经历台的资料像文件夹夹着一叠文件。悬停或聚焦某一张时，目标文件向左抽出约半寸的视觉距离并高亮，文件夹和相邻文件保持稳定。拖入资料有清晰的落点反馈，离开或取消后自然归位。
- 每份 JD 用带塔罗暗纹的卡片呈现。分析开始时，牌组短暂浮起，结果返回后按推荐顺序依次落位。重复分析、切换页面或请求失败后，按钮应可恢复使用。
- 简历优化有明确的「定稿」按钮。保存成功后用小喷壶喷雾和简历卡短暂发光表达完成，像理发后的最后装点。保存失败时显示可处理的结果，减少动效模式下用静态反馈表达相同状态。

## 从问题到验证

1. 先把用户反馈落到一个可验证的结果，记下页面、触发动作、观察到的行为和期望。涉及线上问题时从用户实际打开的完整网址复现。同步 `origin/main`，核对协作更新和未提交改动。通过 [仓库说明](../../../README.md) 找当前模块，提交范围只包含这次改动。
2. 用户报告「无法导入」或看到「静态体验版」时，先区分三层。GitHub 上的源码、腾讯云正在接收流量的部署版本、当前浏览器实际加载的页面和资源。用新标签页或无痕窗口从正式域名打开，必要时给 URL 加上提交号查询参数。只改变 `#resume` 这类锚点可能沿用已加载的页面。
3. 分清本地验证和线上验证。涉及上传时优先用虚构 DOCX 或 PDF 实测文件选择、文字提取、确认成稿和刷新后的保存结果。涉及 AI 时再走 JD 核对、生成建议和保存岗位副本，检查输出依据能追到原稿和 JD。健康接口和 AI 状态只能确认服务及配置，实际解析或模型调用需要单独验证。
4. 涉及交互时用实际浏览器验证，至少覆盖用户触发的那条路径。根据改动范围选测悬停切换、拖拽取消、重复点击、失败后重试、小屏或减少动效。提交前运行相关检查，记录观察结果。
5. 需要发布时，将改动提交到 GitHub `main`，再从该提交部署腾讯云，确认新版本接管流量并在公开网址复测。GitHub 推送和腾讯云更新是两个步骤，以 [腾讯云部署说明](../../../docs/cloudbase-deploy.md) 为准。运行环境中的 DeepSeek 密钥和体验码沿用原配置。纯技能或文档修改可以只同步 GitHub。

在交付里写明实际改善、验证过的路径和发布状态。新的长期偏好补进这份技能，单次微调留在对应实现里。
