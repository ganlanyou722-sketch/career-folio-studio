# 个人经历台与岗位匹配台 · 试用方案 v0.1

用户把散落的论文、比赛 PPT、实习手册和旧简历放进来后，首页先帮他认出有哪些项目；点进项目，能看到哪些事确实由自己做过；选岗位时，能看到哪些事可以拿来证明这份 JD 的要求。三步各自产生可保存、可修改的结果。

## 1　先看一张项目表

首页默认展示项目名、主题、简介、本人贡献、获奖／阶段成果、待核实项。项目名和简介足够建立草稿；上传文件时连这两项也可由系统预填。用户可切换卡片或表格。演示的 Excel 用“项目登记／证据明细”两张表还原这两层，虚构示例均标明，实际用户可替换。

| 字段 | 最合适的填写方式 | 后续用途 |
|---|---|---|
| 项目名称、别名、所属实习／组织、时间 | AI 预填，用户纠正；名称与归属用于判断同名项目 | 找项目、合并材料、形成简历栏目 |
| 主题、简介 | 主题建议 1–3 个；简介写服务对象、解决的问题和达到的阶段 | 列表浏览和初筛；逐句可追溯 |
| 奖项名称、级别、奖次 | 分开存，列表合并显示；无证书或未知级别可空，多次获奖逐条记录 | 竞赛栏目、交付阶段和获奖主体核对 |
| 本人角色与贡献、交付或结果 | 从材料提出候选；只有团队表述时优先询问本人角色 | 判断适配度、形成 STAR，区分背景与个人行动 |
| 材料、原文位置、修订与状态 | 系统维护，点开显示原句；本人补充记录原话 | 核实结论、复用、回溯旧版本 |

前台一行可以是项目、课题、课程实践，或尚未分项目的实习。不同文档归属同一件事时共用一个项目 ID；一个人同一段实习内做的两个独立项目可以各占一行，指向同一个上级经历。校园活动和无奖项的实习具有相同的入库资格。

## 2　上传后的第一分钟

上传后立即显示材料行及解析进度。识别出可能的项目后，给三类可操作结果：“已归入现有项目”“建议新建”“需要你判断”。新用户先看自动整理好的卡；已有简历的用户可以旧简历为索引，把后续资料追加到相应经历。

例：收到同一个校园预约项目的结项 PPT 和个人复盘。左侧显示两份文件，中央只显示一个项目。点“本人贡献”出现原句与出处，用户可修改、拆开、移动到另一项目。团队奖状只补充奖项。若结果数据在两份材料中不同，先核对周期、分母、试点阶段，再决定是否真的冲突。每次只推一个影响较大的问题，可先跳过。

## 3　怎样节省提取和匹配开销

| 发生什么变化 | 复用什么 | 更新什么 |
|---|---|---|
| 相同文件换名重传 | 文件指纹、已解析页段和原出处 | 追加文件别名；用户侧显示已有项目 |
| 一份 PPT 更新了两页 | 其余内容指纹一致的片段和已有事实 | 重新定位页码，重抽变动片段，刷新关联项目摘要与索引 |
| 用户上传一个新 JD | 已确认项目、事实及其索引 | 仅拆本次 JD、召回证据、核对逐项结论 |
| 用户补充一个新事实 | 原有 JD 与无关匹配记录 | 更新该事实的索引，再查哪些已有要求可能新增支持 |
| 用户只调简历字号或位置 | 全部岗位匹配与事实 | 仅新建画布修订；从新修订进入面试时绑定新版 |

实现顺序建议：首版先有稳定 ID、页段定位、去重、事实状态、带版本的关联关系和关键词索引。个人资料库小时，结构化条件＋词库别名足以形成可测基线。用“用户原话和 JD 措辞不同”的样例测漏召，再对同一基线加语义召回；两路结果合并去重，最后回到事实及上下文判断。匹配调用默认带少量相关事实和出处，支持不足时扩大范围。目标岗位不作为硬过滤，避免漏掉可迁移的科研或校园实践。任何缓存须在用户权限范围内，键包含输入修订和规则版本。

## 4　协同到简历和面试

| 使用者 | 收到的数据 | 对用户的呈现 |
|---|---|---|
| 匹配台 | 同一版个人经历、意向、各个 JD 修订 | 意向和证据覆盖分开展示；每个岗位列最有力的证据、最重要缺口、下一步操作 |
| 简历优化台 | 选定 JD、逐项理由、重点项目、可用事实 ID 与原文 | 用内容 skill 生成可接受／拒绝的局部建议。排版与岗位版本由优化台管理 |
| 面试打磨台 | 公司与 JD、实际投递稿修订、对应项目、已证实的动作和结果、仍待补的问题 | 一个案例可展开为背景、本人任务、行动取舍、结果和追问。公司动态单独检索、记录来源 |
| 经历台回写 | 用户在后续工作台明确确认的事实与来源 | “仅用于本次回答／也同步到经历库”；选择同步后，新匹配可采用新事实，旧投递稿继续保留 |

举例：项目“校园自习室预约试点”支持“按环节整理 30 条反馈，提出入口调整建议”；团队资料另支持“两个社团复测”。产品运营 JD 可直接用个人反馈工作。渠道 JD 若要求“独立拓展合作方”，须另找证据。投产品运营时，面试可以追问“为什么先改入口？”并回到分类记录。若追问“留存提高多少？”，当前材料只支持复测事实，正好提示用户还需要什么。

## 5　首轮落地与验证

先在现有 experience、match 两个 skill 插槽试跑同一组虚构样例，再接入解析服务与搜索。输入端已有浏览器材料、选岗和版本界面，加入技能说明可供读取；实际运行还需要调用方执行解析、存储、模型调用与引用校验。

| 验证任务 | 通过条件 |
|---|---|
| 上传两份讲同一项目的材料，再重传其中一份 | 一个项目，两个独立材料来源；重复文件没有新增贡献 |
| 同名比赛不同届次，或一个 PPT 同时介绍两个项目 | 能分开归档；含混项由用户选择，不误合并 |
| 团队复测与个人负责，试点与正式上线 | 事实保留主体、阶段；待核实结论不会写入简历或案例 |
| 一份资料比较产品运营与渠道运营 | 相同材料快照得出不同结论，每一条“直接支持”都能定位 JD 和出处 |
| 修改资料后打开面试包 | 新分析可用新事实；历史投递稿与当时结论可还原 |
| 无 JD、无奖项、无量化结果 | 均可继续整理经历；方向分析、奖项空值和阶段成果分别呈现 |

衡量效率先做小规模人工标注：取不同格式、含重名和近义表达的材料，人工标出正确的项目归属、事实和每条 JD 的有效证据。比较“只搜项目简介”与“事实＋别名＋上下文复核”，记录每条要求前五项找回的有效证据比例、直接支持判断正确比例、一次核对平均耗时、每次新增 JD 重解析旧材料次数。重复文件和仅新增 JD 场景中，旧材料重解析次数目标为 0；涉及个人贡献的生成句必须能追到材料或本人确认。未做真实用户评测前，不宣称某种检索方案已达到最高效率。
